# Fluence.Wpf 1.0 readiness: design specification

Date: 2026-09-04. Branch: `fix/mica-composition-defects`. Current version: `0.8.19-preview`.

Source: the readiness audit (research D). Every claim reused here was re-verified against the
working tree. Corrections to the audit are called out inline and marked "audit correction".

## 1. Summary, goals, non-goals

### Summary

Fluence.Wpf ships 1.0 alongside PSAppDeployToolkit 4.2. 1.0 freezes the public CLR surface and the
public XAML resource key set. This document decides every breaking change, key removal, packaging
change, and documentation fix that must land before that freeze, and states what is deferred.

### Goals

1. Make every breaking change the library will ever want, now, while the policy still allows it.
2. Freeze the surface mechanically, not by review convention. `PublicApiAnalyzers` for CLR members,
   an extended key inventory test for XAML keys.
3. Ship a package a consumer can debug into: SourceLink, portable PDBs, a symbol package.
4. Leave the documentation set free of dead links and stale claims.
5. Prove the release candidate against PSADT 4.2 before the tag exists.

### Non-goals

The documentation website (`docs/roadmap.md` section 5) and the PowerShell module
(`docs/roadmap.md` section 4) are roadmap items. Neither blocks 1.0 and neither is designed here.
Per-control `ThemeResource` override keys, the remaining WinUI control gaps, the RTL audit, and the
per-monitor DPI audit stay on the roadmap. Strong naming is decided in section 4, and the decision
is "no".

### Standing policy this spec assumes

Breaking changes to public API and XAML keys are allowed until 1.0 and are recorded in
`docs/migration-guide.md` in the same commit that makes them. After 1.0, minors are additive only.
PSADT consumes `net472`, seventeen types, and eleven `DynamicResource` keys. Two of those keys,
`FluentFontFamily` and `ApplicationBackgroundBrush`, must keep working. They are aliased, never
renamed away.

## 2. Public API changes

### 2.1 Audit corrections

Three types the audit listed for internalisation are already `internal` in the tree:
`Controls.CaptionButtonChrome` (`Controls/CaptionButtonChrome.cs:40`),
`Controls.LoopingItemsSource` (`Controls/LoopingItemsSource.cs:48`), and
`Controls.LoopingSelectorPlaceholder` (`Controls/LoopingSelectorPlaceholder.cs:43`). The audit read a
stale `bin/Debug/net472` assembly. Four types remain, not seven.

The audit counts fifteen bare `EventHandler` events. The tree has thirteen. There are no bare
`EventHandler` events outside `Fluence.Wpf/Controls`; both static manager events are already typed.

### 2.2 Event args rule

The rule for 1.0, to be written into `AGENTS.md` section 5: a Fluence event uses
`EventHandler<TArgs>` when WinUI's counterpart carries typed args, and bare `EventHandler` when
WinUI passes `object`. A WPF `RoutedEvent` is used only where the event must tunnel or bubble through
a template, which is the six existing routed events and no more. Applying that rule, four of the
thirteen bare events gain args and nine keep `EventHandler` by design.

New args types and their members:

| Type | Base | Members | WinUI basis |
| --- | --- | --- | --- |
| `ContentDialogOpenedEventArgs` | `EventArgs` | none | `ContentDialogOpenedEventArgs` has no members |
| `ContentDialogClosedEventArgs` | `EventArgs` | `ContentDialogResult Result { get; }` | `ContentDialogClosedEventArgs.Result` |
| `InfoBarClosedEventArgs` | `EventArgs` | `InfoBarCloseReason Reason { get; }` | `InfoBarClosedEventArgs.Reason` |
| `TeachingTipClosedEventArgs` | `EventArgs` | `TeachingTipCloseReason Reason { get; }` | `TeachingTipClosedEventArgs.Reason` |
| `InfoBarCloseReason` (enum) | n/a | `CloseButton`, `Programmatic` | WinUI `InfoBarCloseReason` |
| `TeachingTipCloseReason` (enum) | n/a | `CloseButton`, `LightDismiss`, `Programmatic` | WinUI `TeachingTipCloseReason` |

`InfoBarClosingEventArgs` gains `InfoBarCloseReason Reason { get; }` alongside its existing `Cancel`,
matching WinUI. That is additive to an existing type and is done now so the two args classes agree.

Each new args class lives in its own file under `Fluence.Wpf/`, matching the forty-six existing
root-namespace types.

## 3. XAML keys

### 3.1 Dead key removal

Remove these Colors and their brush twins from `Themes/Colors/Theme.Light.xaml`,
`Theme.Dark.xaml`, and `Theme.HighContrast.xaml`, and remove the matching hand-written brush entries
from `Theming/SpecialBrushes.cs`:

| Key family | Twins | Reason |
| --- | --- | --- |
| `WindowCloseFillColorHover`, `WindowCloseFillColorPressed`, `WindowCloseForegroundHover`, `WindowCloseForegroundPressed` | 4 | duplicate of `WindowCloseButtonBackgroundPointerOver`, `...Pressed` and `...ForegroundPointerOver` at identical values; `SpecialBrushes.cs:499` already labels them unconsumed |
| `ControlStrokeColorTertiary` | 1 | no WinUI counterpart, no template consumer |
| `SystemFillColorInformational` | 1 | no WinUI counterpart; `SystemFillColorAttention` is the WinUI role and is already published |
| `KeyboardFocusBorderColor` | 1 | no consumer; `FocusStrokeColorOuter` and `Inner` are what the focus visuals bind |

That is 23 keys with the twins counted. Three follow-on edits are mandatory in the same commit.
First, `Fluence.Wpf.Demo/Pages/GalleryColorsPage.xaml.cs` lists two of them as swatches and must drop
those rows. Second, `Fluence.Wpf/Properties/DesignTime.Light.xaml` and `DesignTime.Dark.xaml` are
generated and must be regenerated, or `Fluence.Wpf.Tests/Theming/DesignTimeResourceTests.cs` fails.
Third, the three golden snapshots under `Fluence.Wpf.Tests/Theming/golden/` must be regenerated.

CHANGELOG note, under `### Removed` in the 1.0.0 section:

"Removed twenty three unconsumed theme keys rather than freeze them into the 1.0 surface:
`WindowCloseFillColorHover`, `WindowCloseFillColorPressed`, `WindowCloseForegroundHover`,
`WindowCloseForegroundPressed`, `ControlStrokeColorTertiary`, `SystemFillColorInformational`,
`KeyboardFocusBorderColor`, and their `*Brush` twins. The caption button colours remain published
under their WinUI style names `WindowCloseButtonBackgroundPointerOver`,
`WindowCloseButtonBackgroundPressed` and `WindowCloseButtonForegroundPointerOver`. Use
`SystemFillColorAttention` in place of `SystemFillColorInformational`, and `FocusStrokeColorOuter` in
place of `KeyboardFocusBorderColor`."

### 3.2 Template internal styles

`Themes/Generic.xaml` merges 51 dictionaries into `Application.Resources`, so every `x:Key` in
`Themes/Controls/**` and `Themes/Icons/FluenceIcons.xaml` is publicly resolvable. The tree carries 77
unique keys there. The audit's 57 is the subset with a single consumer and no deliberate design as
API.

Two options were on the table: keep them public with documentation, or move them into per-template
resources. The rule chosen, applied uniformly:

**Keys defined under `Themes/Controls/**` and `Themes/Icons/**` are not public API. They stay where
they are, and `docs/theming.md` states that they are unsupported and may change in any release.**

Moving 77 keys into per-template `<ControlTemplate.Resources>` was rejected. Several are shared
across templates in the same file, several are referenced by `Storyboard.TargetName` from a sibling
template, and the change is a large edit whose failures surface only at runtime, for no consumer
benefit. Freezing them by accident is prevented by documentation plus the inventory test scoping in
section 3.4, not by relocation.

Two exceptions to the rule, kept public and documented as such because a consumer legitimately reuses
them: `DefaultControlFocusVisualStyle` and `DefaultCollectionFocusVisualStyle`. PSADT binds none of
the 77, so nothing else needs preserving.

### 3.3 Aliases and one rename

| Key | Action | Detail |
| --- | --- | --- |
| `FluentFontFamily` | alias | `Themes/Typography/Typography.xaml` gains `ContentControlThemeFontFamily` as a second key pointing at the same `FontFamily`. `FluentFontFamily` stays and stays supported for the life of 1.x. `docs/theming.md` names `ContentControlThemeFontFamily` as preferred. |
| `ApplicationBackgroundBrush` | alias | `SpecialBrushes.cs:72` also writes `ApplicationPageBackgroundThemeBrush` from the same `ApplicationBackgroundColor`. Both keys ship. `ApplicationBackgroundColor` also stays. |
| `NavigationViewSelectionIndicatorBrush` | rename | becomes `NavigationViewSelectionIndicatorForeground`, matching WinUI. Fourteen internal references update. No consumer outside the library. Migration note: "`NavigationViewSelectionIndicatorBrush` is now `NavigationViewSelectionIndicatorForeground`." |

Aliasing rather than renaming is chosen for the first two because a renamed `DynamicResource` key
fails silently. A PSADT dialog with no `ApplicationBackgroundBrush` renders transparent with no error
and no build failure, which is the worst failure mode available.

### 3.4 Key inventory test

`Fluence.Wpf.Tests/Theming/ThemeParityTests.Rebuilt_MatchesGoldenResolvedValuesAsync` already asserts
every key and value of the computed dictionary against `Theming/golden/{Light,Dark,HighContrast}.txt`.
It covers slot `[0]` only. It is extended to carry the freeze:

1. A new test `PublicKeyInventory_MatchesFrozenSet` captures the keys visible in
   `Application.Resources` after `ApplicationThemeManager.Apply`, filters out every key whose
   defining dictionary has a `Source` under `Themes/Controls/` or `Themes/Icons/`, and compares the
   remaining set against `Fluence.Wpf.Tests/Theming/golden/PublicKeys.txt`.
2. `PublicKeys.txt` is generated once at the 1.0 commit and committed. It holds the slot `[0]` keys,
   the `Themes/Typography/Typography.xaml` keys, and the two documented focus visual styles.
3. The test fails on a removed key and on an added key. An intentional addition updates the file in
   the same commit, which is the `PublicApiAnalyzers` workflow applied to XAML.
4. `docs/roadmap.md:43` is corrected: the mechanism exists and is being extended, not built.

### 4.1 `docs/release.md` rewrite outline

The file becomes a description of one action plus its preconditions, not a manual checklist of build
commands.

1. Preconditions. Green CI on `main`. `CHANGELOG.md` has a dated section for the version with no
   `Unreleased` content left. `PublicAPI.Unshipped.txt` is empty for every TFM.
   `docs/migration-guide.md` has an entry for every breaking change in the section.
2. Bump. Edit `VersionPrefix` and `VersionSuffix` in `Directory.Build.props`. Nothing else carries a
   version.
3. Tag. `git tag v1.0.0` and push the tag. Everything after this is CI.
4. What CI does: builds Release, runs both TFM test lanes, packs, checks the tag against the version,
   creates the GitHub release with the per-TFM zips and the CHANGELOG slice, and pushes the `.nupkg`
   and `.snupkg` to nuget.org.
5. What to verify afterwards: the package page lists the symbol package, and a debugger can step into
   a library source file from a consuming project.
6. Screenshots. The existing rule stays: regenerate `docs/screenshots/` before tagging when gallery
   visuals changed.

### 4.2 CHANGELOG

Four defects are fixed before 1.0.

1. Add link reference definitions at the foot of the file, one per version, in the Keep a Changelog
   comparison form `https://github.com/sintaxasn/Fluence.Wpf/compare/vA...vB`, plus an `[Unreleased]`
   link against `main`.
2. Normalise every `-Preview` heading to `-preview`, matching the identifier that actually shipped.
3. Add the missing `0.8.3`, `0.8.4`, and `0.8.14` headings. Where no record survives, the section
   carries one `### Changed` bullet saying the release was an internal build with no recorded
   consumer-visible change.
4. Give `[0.5.0]` its `### Added` subsection.

Entry shape for 1.0 onward: one sentence per bullet. Design rationale moves to `docs/winui-parity.md`.
The existing `Unreleased` paragraphs are reshaped as part of assembling the `1.0.0` section, not
before.

The `1.0.0` section carries `### Added` (the four new args types, the two new close reason enums, the
two alias keys, `InfoBarClosingEventArgs.Reason`, three automation peers), `### Changed` (the three
enum renames, the four retyped events, the two retyped routed events, the

### 5.5 README rewrite outline for a 1.0 landing

1. Banner image, one sentence describing the library, then a badge row: NuGet version, NuGet
   downloads, CI status, license, target frameworks.
2. Install. One `dotnet add package Fluence.Wpf` line and the `PackageReference` equivalent.

### 6.3 Template part and visual state attributes

`ContentDialog` uses `PART_DialogOverlayHost` (`Controls/ContentDialog.cs:69`) with no

## 7. Consumer verification

`AGENTS.md` section 11 allows PSADT paths as release gate evidence. The gate runs once against the
release candidate, and again if any breaking change lands after it.

1. Build the candidate in this repository. `dotnet build Fluence.Wpf.sln -c Release`, expecting zero
   warnings and zero errors on all three TFMs.
2. Update the vendored subtree. The PSADT checkout at `F:\Consolidation\PSADT-main` carries Fluence
   at `vendor/Fluence.Wpf`, referenced by
   `src/PSADT.UserInterface.Interfaces/PSADT.UserInterface.Interfaces.csproj:14`. Sync the candidate
   tree into `vendor/Fluence.Wpf` on a scratch branch in that checkout.
3. Restore and build PSADT. Its `packages.lock.json` pins `0.8.19-preview`, so the version bump means
   a lock file regeneration in that repository. Expect that, and record it as a step the PSADT side
   must take at its own 4.2 release.
4. Compile check the seventeen consumed types and their members. A clean build of
   `PSADT.UserInterface.Interfaces` covers all of them, because every use is a compile time
   reference. None of the removals in section 2 touch what PSADT uses, so this build is expected to
   pass unchanged.
5. Resource key check, which no compiler covers. Run the PSADT client and open each Fluence dialog:
   CloseApps, Custom, Input, ListSelection, Progress. Confirm each renders with a solid background,
   correct fonts, and correct accent fills. The eleven bound keys are `ApplicationBackgroundBrush`,

## 10. Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| A renamed `DynamicResource` key fails silently downstream | a PSADT dialog renders transparent with no error | never rename a PSADT bound key. Alias both `FluentFontFamily` and `ApplicationBackgroundBrush` and keep both for the life of 1.x. Section 7 step 5 is a visual check precisely because no compiler covers this. |
| The golden snapshots and the design time XAML drift out of sync during the key removal | test failures that look like a regression | regenerate both in the same commit as the removal, and name the generator for each in the commit body. |
| `PublicAPI.Shipped.txt` is generated too early and freezes a surface still in flux | the analyzer fights every later change in the same release | phase C runs after A, B and D. Nothing in phase E or F touches public API. |
| `DebugType` moving from `full` to `portable` breaks a consumer's symbol tooling | a debugger stops resolving symbols | portable PDBs are supported by every debugger the supported TFMs target, `net472` on Visual Studio 2019 and later included. Note the change under `### Changed`. |
| Enabling automated NuGet publish makes a mistaken tag irreversible | a bad 1.0.0 on nuget.org can only be unlisted, not replaced | the tag guard runs before the push, the publish runs only after both test lanes pass, and the RC tag in phase G exercises the whole path first. |
| The 122 link strip in `docs/controls.md` is a large mechanical edit | a botched pass damages content | do it in one scripted pass, review the whole diff, and confirm no `<a href` remains in the file. |
| PSADT 4.2 slips, leaving 1.0 without its coordinating release | 1.0 ships with an unproven consumer | section 7 runs against PSADT `main` at the time of the RC, not against a released 4.2. The evidence is the build, not the release date. |
| The version collapse silently ships the wrong version | a package labelled 0.8.19 published as 1.0.0 | the csproj duplicates currently win over the props file, which is exactly that failure. Deleting them, plus the CI tag guard, closes it from both sides. |
| Splitting large files during 1.0 introduces regressions under time pressure | a late defect in `NavigationView` or `FluenceWindow` | the splits are deferred to 1.x by design. Nothing in phases A through I touches them. |
| The three new automation peers change screen reader output for existing consumers | a consumer's accessibility test breaks | peers are additive and the current output is a bare `FrameworkElement`, so any change is an improvement. Note them under `### Added`. |
