## Problem and outcome

The `FluenceWindow` startup and backdrop code had accumulated explanations and interop from several experiments. The goal was a smaller, understandable shell implementation that preserves the current visible behavior. An apparent lack of flashing in another framework was a comparison to test, not proof that any Fluence step was redundant. No production staging, cloak, offscreen move, layered-alpha hold, or presentation timer was found in the reviewed window path.

The first phase established a source/test baseline, deleted two unused interop entry points and one generator entry, and ran an opt-in standalone comparison probe. Later local window commits centralized shell setup and caption rules, inlined fixed chrome setup, moved transition readiness into the overlay, simplified maximize hit testing, and clarified the optional icon fallback. The work did not remove either background write or full-glass setup. A larger rewrite remains outside the accepted scope.

## Existing path and upstream comparison

`FluenceWindow` constructs its `WindowChrome`, then configures the HWND in `OnSourceInitialized`. `ApplyBackdrop` resolves one `BackdropPlan`, sets `Window.Background` and `HwndSource.CompositionTarget.BackgroundColor`, and applies the native DWM choices. The chrome's `GlassFrameThickness` controls how much of the client area DWM can draw behind. Tests currently check the two background values across a backdrop swap and check that a shown window is not cloaked. The cloak query currently returns zero both for not cloaked and for a failed read, so that assertion is useful but not conclusive in an unsupported session.

Official WPF source shows that its Fluent backdrop path also clears the composition target, extends a full glass frame, then applies the DWM backdrop attribute before `ShowWindow`. `WindowChromeWorker` independently makes the target transparent when glass is active. This makes Fluence's explicit target assignment a candidate for duplication on one path, but its fallback and theme-swap roles are still open questions. WPF's `HwndTarget` handles `WM_ERASEBKGND` itself. WinUI's `Window.SystemBackdrop` is integrated with its compositor and handles material fallback internally. Neither comparison proves that a Fluence change will be flash-free. A [WPF issue](https://github.com/dotnet/wpf/issues/10513) also reports a dark Fluent window flashing white on first show.

## Options

### A. Retain the custom shell and make one pre-show policy explicit (selected)

The executed work kept `WindowChrome` and Fluence's `BackdropPlan` as the cross-target policy owner, centralized shell application, and removed proven dead interop. The probe found overlapping target ownership under its recorded condition, but that did not justify deleting Fluence's explicit target write. The custom title bar and all three library target frameworks remain part of the contract.

### B. Return to native caption and native frame

The OS owns caption painting and much of the first visible surface. That can reduce custom chrome work, but changes caption overrides, title-bar interactions, geometry, snap behavior, and the established visual contract. This is a separate redesign with a broader acceptance and accessibility review, not a simplification of the current control.

### C. Hand modern targets to WPF Fluent backdrop

.NET 10 and 11 contain an internal WPF backdrop manager, but it is bound to WPF Fluent theme state rather than a supported callable public policy API. It does not cover `net472`, and a handoff would split material and fallback policy across target frameworks. Its internal enum has more than Mica, yet it does not expose Fluence's requested backdrop choice as a stable public WPF interface. This option needs a new compatibility design and does not meet the bounded first phase.

## Original causal experiment and decision rule

The following protocol is preserved as the original design, not a claim that every row or environment was completed. The actual acquisition used 150% DPI and probe-only topmost windows; the deviations and limits are recorded below.

An opt-in standalone probe compares four fresh-process window modes: plain solid `Window` with Fluence resources; plain `Window` with matching `WindowChrome` and explicitly requested DWM backdrop; current `FluenceWindow` with a requested backdrop; and, on .NET 10 only, WPF's built-in Fluent window with its default backdrop policy and no Fluence theme engine. Plain solid and WPF Fluent do not accept a requested material. Record actual DWM backdrop readback and query status, and do not describe all four modes as material-matched. Each process selects `default` or `software-only` through `RenderOptions.ProcessRenderMode` before creating the application, loading theme resources, or creating any HWND; record both the preference and actual WPF rendering tier. In the plain chrome mode, switches isolate whether the probe makes an explicit target-clear write, requests full glass, or sets the DWM backdrop. `WindowChrome` itself may clear the target, so skipping the probe's explicit write cannot establish that a transparent target is unnecessary. A separate diagnostic intervention can force an opaque target after chrome initialization to test its visible effect; it is never a production fallback proposal. Log the actual target color after each step. The probe records runtime, OS/session, theme, DPI, rendering tier, HWND style and geometry, queried DWM attributes and query failures, and event timestamps. It must distinguish a value successfully read from a default returned after a failed query. It cannot infer the HRESULT of a Fluence native call it did not observe or read back DWM frame margins through a nonexistent getter.

An external compositor recording begins before each `Show` and samples a fixed, known, unoccluded window region including its border. Record frame rate, dropped frames, and sampling gaps; a missed transient is not a pass. In RDP, record the delivered client pixels as well as the server-side trace. `RenderTargetBitmap` and a settled `PrintWindow` image cannot show the native first present. `ContentRendered`, the first `CompositionTarget.Rendering` callback, and `DwmFlush` are timing clues, not proof of a complete DWM-presented window. The minimum current-host set compares Dark startup across plain solid, requested Mica chrome-DWM, requested Mica Fluence, and WPF Fluent default policy, with three fresh-process launches per mode. It also pairs three software-only chrome-DWM and Fluence launches at the same geometry with requested Mica, accepting a material match only when actual DWM readback supports it, and varies one chrome ingredient at a time under default rendering. Separate control runs cover Fluence Light Mica and Dark None; live buttons drive Light to Dark to Light, backdrop swap, and `SizeToContent` growth in one window. Capture High Contrast manually on the current host. Additional backdrop, DPI, Windows 10, RDP, and .NET 11 branches remain explicitly unverified until exercised.

The plain-window comparisons can identify likely mechanisms but cannot authorize removal of Fluence's target-color write. Such a change requires a later isolated Fluence branch that removes only that write, repeats the first-show comparison and full affected regression matrix, and keeps the change only if no regression is observed in supported environments. If a comparison cannot distinguish two paths because of capture limits, retain the current behavior. A failed DWM call or query must be shown as a failed observation, never counted as successful fallback. The first phase stops with an evidence report and a reviewed recommendation for that next patch.
